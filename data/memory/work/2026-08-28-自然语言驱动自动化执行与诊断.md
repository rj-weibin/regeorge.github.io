# 自然语言驱动自动化执行与诊断

## 原始观察

> 近期我的自动化工作流中，支持自然语言驱动 指定环境执行自动化任务，并自动分析执行报告，找出问题分布，前置失败、疑似业务问题等，对于非结构化的问题快速定位有提效作用。

## 这次变化是什么

过去的重点是把自然语言业务描述转成自动化用例。现在，工作流继续向运行阶段延伸：人只需要说明目标环境、执行范围和希望回答的问题，Agent 负责把意图路由到环境触发、报告聚合和失败分析能力。

执行结束后，结果不再停留在通过率和失败列表。工作流会先做确定性统计，再按业务域缩小问题分布，最后结合首个失败节点、前置造数链、步骤请求响应、运行日志和代码核实，区分环境依赖、前置失败、用例逻辑、自动化不稳定与疑似业务问题。

这使自然语言不只用于“生成代码”，也开始成为操作自动化系统和消费诊断结果的入口。

## 已验证工作流

```text
自然语言目标
→ 解析目标环境与执行范围
→ 匹配环境类型和任务类型
→ 触发并跟踪有效执行
→ 聚合任务、用例和失败明细
→ 按业务域与变化类型缩小搜索面
→ 结合步骤、日志和代码形成根因假设
→ 输出优先级与下一步动作
```

其中：

- 环境执行已有 `env-trigger` 规则入口，可按目标环境触发全量或指定任务。
- 环境报告已有 `env_report` 服务，可按环境读取任务结果，并排除被中断执行产生的“假完成”记录。
- 深度归因已有 `failure-analyzer` 能力，按首个失败节点、父目录造数链、运行日志和代码核实形成证据链。
- 跨报告比较与“疑似业务问题”判断已经在 Agent 工作流中跑通，但还没有全部收敛为无人值守 Service。

## 一次真实样本

2026-08-28 的一次指定环境全量执行覆盖 9 个标准任务：

| 指标 | 结果 |
|---|---:|
| 总用例 | 7,949 |
| 成功 | 7,084 |
| 失败 | 865 |
| 通过率 | 89.1% |

第一轮自动分析把 865 个失败按业务域压缩为 5 个问题分布：

| 问题分布 | 数量 |
|---|---:|
| 认证 / 接入 | 293 |
| 运营商 / 计费 | 173 |
| 查询 | 70 |
| 绑定 / IP 校验 | 33 |
| 其他 | 296 |

在此基础上，跨执行对比进一步识别出：

- 105 个此前通过、本次新增的周期计费补偿类失败，步骤证据指向页面变量提取为空和计费接口异常，形成“环境或业务状态变化”的待验证假设。
- 712 个持续失败的 case ID，优先回到前置数据、时序依赖和断言错位等已知问题，不与本次新增异常混在一起。
- 个别任务通过率相较上次明显下降，可优先检查对应认证链路或外部依赖，不再从 865 条失败中逐条盲查。

## 为什么对非结构化问题有效

自动化失败往往同时混有环境、数据、时序、接口、断言和业务行为变化。人工从失败列表逐条阅读时，很难先判断应该查哪一层。

这套工作流先做两轴切分：

1. **问题发生在哪里**：按认证、计费、查询、绑定等业务域聚类。
2. **问题为什么发生**：按新增失败、持续失败、前置 / 时序、环境依赖、用例问题和疑似业务问题分层。

第一轴负责压缩搜索面，第二轴负责决定下一步证据。它不能替代根因确认，但可以更快把人工注意力送到最有区分度的位置。

## 能力边界

- 自然语言入口由 Agent 解释并路由到现有能力，不是测试平台原生提供的自然语言接口。
- 按用例名做关键词聚类只能描述问题分布，不能单独确认根因。
- “疑似业务问题”必须继续核对步骤级请求响应、环境日志、代码逻辑或单条复现，不能由报告直接定案。
- 当前样本证明工作流可用，但尚未形成长期效率指标；“提效”仍需用首次形成有效假设的耗时、人工点击数、误判修正率和有证据归因覆盖率持续度量。

## 对个人工程论的更新

自动化工作的价值不只在于建设更多用例，也在于让人可以用更接近业务意图的语言操作系统，并让执行结果自动转化为可判断、可追踪的问题结构。

人的角色继续向上移动：定义目标、审查证据、裁决疑似业务问题和优化诊断规则。Agent 负责执行、聚合、聚类、检索证据和提出下一步验证路径。
