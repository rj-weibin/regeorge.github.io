项目主张

Why → How → What changed

WHY · 问题

错误理解会被批量放大

手工用例、页面行为和接口行为可能不一致；只追求生成数量，会把错误设计快速复制。

HOW · 判断

先收敛意图，再扩大规模

让 AI 辅助拆解和探测，让人工负责业务预期、边界取舍和放行判断。

WHAT · 产出

形成可复用的测试生产线

把流程、公共能力、审计规则和失败经验组织成持续工作的工程资产。

生产线流程

五个阶段串成一条线：每阶段都有输入、产物和停止条件；下方用一个真实样本走完全程

01意图收敛
输入需求草稿 / 页面行为 / 接口假设
动作拆状态矩阵、数据构造方式、验证命题
产物Phase 0 审核清单（状态·数据·命题）
停止：审核不通过 → 不进入规模化
→
02样本设计
输入Phase 0 审核清单
动作挑代表场景与公共能力先验证
产物通过样本 + 公共步骤雏形
停止：样本无法稳定复现 → 回头补意图
→
03真实校准
输入通过样本
动作对照页面行为 / 请求 / 结果
产物校准后的断言与变量契约
停止：页面/接口不一致 → 记录缺口
→
04批量落地
输入已验证模式
动作复用生成剩余用例并回填
产物大批用例 + 回填结果
停止：出现未知失败模式 → 暂停扩量
→
05审计回流
输入执行结果 / 失败
动作定位首个失败，归因（环境/平台/设计/产品）
产物规则与边界沉淀
停止：归因不清 → 归为不可自动化

一个真实样本如何穿过生产线

以「费用管理」为例：56/56 全量调试通过并完成回填

意图收敛先确认费用状态矩阵、数据构造与验证命题，审核通过才批量
样本设计挑代表费用场景先验证，沉淀公共步骤雏形
真实校准对照页面金额、请求与结果，校准断言与变量契约
批量落地复用已验证模式生成剩余用例，完成 56/56 回填
审计回流全量 PASS 即闭环；同类问题（如设备管理 89 条定位到的接口异常）沉淀为规则

工程结构

四层协作，而不是一组孤立脚本

LAYER 01

能力层

封装登录、数据准备、平台交互和探测等重复动作。

LAYER 02

编排层

按 Phase 0、样本、批量和审计阶段推进任务。

LAYER 03

资产层

沉淀公共步骤、变量契约、失败模式和验证规则。

LAYER 04

边界层

当信息不足时让 Agent 停下，记录缺口而不是扩散数量。

关键工程判断

决定生产线质量的四个门

Phase 0 是阻断门

批量创建前先确认状态矩阵、数据构造和验证命题；审核不通过，就不进入规模化执行。

PASS 必须回到业务命题

接口成功不等于业务验证成功。样本、断言、清理和失败归因都进入审计。

公共能力服务于差异化验证

复用不是为了减少代码，而是把精力放到变化的业务状态和判断上。

失败先归因，再修复

区分环境、平台、设计和产品行为，避免把所有失败都归因于脚本。

验证结果

质量闭环的高置信证据

56/56费用管理全量调试通过并完成回填
82 条运营商 VLAN完成共性修复和全量审计
89 条设备管理串行复检 100% PASS，并定位接口异常
46 条接入时段全部 PASS，并补齐字段约束
34/34简网络界面集中修复变量链、导入和断言问题

规模不是终点

1300+ 条用例、约 85% 自动化率和约 94% CI 成功率，只作为阶段背景；真正支撑判断的是右侧这些能够复核的案例证据。

复杂场景自动化准入

四道门串成一条线：任一门不过，就暂不创建公共用例

停止：意图不清 → 记录缺口
→

输入数据方案

输入可复现触发

停止规则：任一环节无法说明，暂不创建公共用例，记录缺失的数据、触发条件和可观测结果，归为“当前不可自动化 / 信息不足”。
